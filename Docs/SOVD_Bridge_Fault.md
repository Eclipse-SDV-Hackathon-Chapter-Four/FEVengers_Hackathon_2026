# SOVD Fault Bridge – Doctor Whodunit (FEVengers)

> Created with AI assistance (Claude Opus 5.5, Anthropic).

> **Historical.** The SOVD fault bridge described here was used until the OpenSOVD gateway replaced it (same DFM query interface, standard SOVD path, port 7690; see [`opensovd-gateway-dfm.md`](opensovd-gateway-dfm.md)). Its code (`sovd/sovd-fault-bridge/`) was removed from the repository on 7 October 2026, so the build and run commands below no longer work. The code is in the git history up to commit `0fda212` (`git show 0fda212:<path>`). The DFM finding in section 9 is still valid.

Exposes faults stored in the Eclipse OpenSOVD **Diagnostic Fault Manager (DFM)** over a SOVD-style REST `/faults` API.

Status: working end to end on Ubuntu (Podman) with the DFM container and `tst_app`. Hackathon quick fix, not following upstream coding guidelines, not intended for upstream as is.

---

## 1. Why this exists

| Component | `/faults` today |
|---|---|
| OpenSOVD CDA (`classic-diagnostic-adapter`) | Works, but only for UDS ECUs (translates to UDS `19` / `14`) |
| OpenSOVD server/gateway (`opensovd-core`) | No faults route and no fault provider |
| DFM (`fault-lib`, `dfm_lib`) | Stores faults and answers queries over iceoryx2 (`dfm/query`), but has no REST interface |

The DFM is OpenSOVD's central fault memory for HPC software, but nothing serves its faults over SOVD yet. This bridge fills that gap.

**Limitation:** the bridge is a standalone HTTP server, so the OpenSOVD server is **not** in the fault path. The proper integration is a `FaultProvider` inside `opensovd-core` (see section 8), to be aligned with the OpenSOVD maintainers.

## 2. Architecture

```
Tester / Evidence collector
        │  HTTP REST  :7691  /sovd/v1/components/{entity}/faults
        ▼
┌─ Container: sovd-fault-bridge (Rust, axum) ─┐
│  HTTP routes → Iceoryx2DfmQuery client       │
└──────────────┬──────────────────────────────┘
               │ iceoryx2 request/response "dfm/query" (shared memory)
               ▼
┌─ Container: DFM (dfm_bin) ───────────────────┐
│  query server → fault store (KVS, /store)    │
└──────────────▲───────────────────────────────┘
               │ iceoryx2 publish (fault records)
┌─ Container: reporter (tst_app / Guardian) ───┐
│  fault_lib Reporter                          │
└──────────────────────────────────────────────┘
```

- The bridge uses the DFM's own query client, `dfm_lib::Iceoryx2DfmQuery`, which implements `DfmQueryApi`.
- `{entity}` is the SOVD path the reporter publishes under. For `fault_lib` reporters this is the **fault catalog id** (`hvac`, `battery`).
- iceoryx2 is shared-memory IPC on one machine. All containers must share the host IPC namespace, PID namespace, `/dev/shm` and `/tmp/iceoryx2`.

## 4. API

Base: `http://<host>:7691/sovd/v1`

| Request | DFM call | Response |
|---|---|---|
| `GET /components` | none | Configured entities (`--entities`) |
| `GET /components/{entity}/faults` | `get_all_faults` | `{"items": [fault, …]}` |
| `GET /components/{entity}/faults/{code}` | `get_fault` | `{"item": fault, "environment_data": {…}}` |
| `DELETE /components/{entity}/faults` | `delete_all_faults` | `204 No Content` |
| `DELETE /components/{entity}/faults/{code}` | `delete_fault` | `204 No Content` |
| `GET /health` | none | `{"status":"ok"}` |

Fault JSON uses the field names of the CDA's `Fault` / `FaultStatus` (`cda-sovd-interfaces`), so both sources look the same to a tester:

```json
{
  "code": "hvac.blower.speed_sensor_mismatch",
  "display_code": "hvac.blower.speed_sensor_mismatch",
  "scope": "ecu",
  "fault_name": "BlowerSpeedMismatch",
  "severity": 4,
  "status": {
    "test_failed": false,
    "test_failed_this_operation_cycle": false,
    "pending_dtc": false,
    "confirmed_dtc": false,
    "test_not_completed_since_last_clear": false,
    "test_failed_since_last_clear": false,
    "test_not_completed_this_operation_cycle": false,
    "warning_indicator_requested": false,
    "mask": "0x00"
  },
  "symptom": "Human-readable summary",
  "occurrence_counter": 0,
  "aging_counter": 0,
  "healing_counter": 0
}
```

`status` uses ISO 14229 DTC status bits; `mask` is the combined byte.

Errors:

| DFM result | HTTP | Meaning |
|---|---|---|
| `NotFound` | 404 | Unknown entity or fault code |
| `BadArgument` | 400 | Malformed request |
| `Storage(...)` | 503 | DFM not reachable or query timeout (default 1 s) |

Command-line options:

| Option | Default | |
|---|---|---|
| `--listen` | `0.0.0.0:7691` | HTTP address |
| `--entities` | `battery` (image default: `battery,hvac`) | Listed under `/components` |
| `--dfm-timeout-ms` | `1000` | Timeout per DFM query |

## 6. Run and test (Ubuntu)

Clean state first (stale iceoryx2 files cause timeouts):

```bash
podman rm -f bridge dfm
sudo rm -rf /tmp/iceoryx2/* ; sudo rm -f /dev/shm/iox2_*
mkdir -p /tmp/iceoryx2
```

Terminal 1 – DFM (start first, wait for `DFM transport listening...`):

```bash
podman run -d --name dfm --ipc=host --pid=host \
  -v /dev/shm:/dev/shm -v /tmp/iceoryx2:/tmp/iceoryx2 \
  localhost/dfm:dev
podman logs -f dfm
```

Terminal 2 – bridge, faults, query:

```bash
podman run -d --name bridge --net=host --ipc=host --pid=host \
  -v /dev/shm:/dev/shm -v /tmp/iceoryx2:/tmp/iceoryx2 \
  localhost/sovd-fault-bridge:dev
podman logs bridge

podman run --rm --ipc=host --pid=host \
  -v /dev/shm:/dev/shm -v /tmp/iceoryx2:/tmp/iceoryx2 \
  --entrypoint /usr/local/bin/tst_app \
  localhost/dfm:dev -c /catalogs/hvac_fault_catalog.json

B=http://127.0.0.1:7691/sovd/v1
curl -s $B/components | jq
curl -s $B/components/hvac/faults | jq
curl -s -i -X DELETE $B/components/hvac/faults
```

Podman options:

| Option | Needed on | Why |
|---|---|---|
| `--ipc=host` | DFM, bridge, reporter | iceoryx2 shared memory across containers |
| `--pid=host` | DFM, bridge, reporter | iceoryx2 detects dead peers by PID; separate PID namespaces leave stale services |
| `-v /dev/shm:/dev/shm` | DFM, bridge, reporter | Shared memory segments |
| `-v /tmp/iceoryx2:/tmp/iceoryx2` | DFM, bridge, reporter | iceoryx2 discovery files |
| `--net=host` | bridge | REST port reachable; avoids the rootless IPv6 port-forward reset |

The iceoryx2 warning `Config::global_config() ... No config file was loaded` is harmless.

DFM logs each fault at INFO level:

```
Received new fault ID: Text("hvac.blower.speed_sensor_mismatch")
process_record{path="hvac"}: ... Fault ID ... stored
```

### AutoSD

Same commands inside the VM, plus `--security-opt label=disable` on every container (SELinux). Transfer the image:

```bash
podman save -o bridge.tar localhost/sovd-fault-bridge:dev
scp -P 2222 bridge.tar root@localhost:/root/
ssh -p 2222 root@localhost podman load -i /root/bridge.tar
```

Reach the REST port from the laptop with an SSH tunnel:

```bash
ssh -p 2222 -L 7691:localhost:7691 root@localhost
```

## 7. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `503 storage error: query timeout` | DFM not running or not reachable | `podman ps -a`; restart DFM; clean iceoryx2 state (section 6); same IPC options on all containers |
| `tst_app` panics `CatalogVerification(Timeout)` | Same: DFM not answering the catalog handshake | As above |
| `dfm Exited (137)` | DFM killed | Restart; add `--restart=always` (Ankaios: `restartPolicy: ALWAYS`) |
| `curl: Recv failure: Connection reset by peer` | Rootless port forward over IPv6 | Use `--net=host`, or `127.0.0.1` instead of `localhost` |
| Faults listed but all status bits `false` / `mask 0x00` with `hvac` catalog | DFM debounce behavior (section 9) | Use a catalog without manager-side `EdgeWithCooldown` |
| `error: get_value could not find key: hvac` in DFM log | First access to an empty KVS | Harmless |

Restarting the DFM wipes its fault memory (`/store` is inside the container). Mount a volume to keep it: `-v dfm-store:/store`.

## 9. Finding: DFM drops re-occurring faults with manager-side `EdgeWithCooldown`

Observed with the `hvac` demo catalog (`BlowerSpeedMismatch`, `manager_side_debounce: EdgeWithCooldown 100 ms`) and `tst_app` toggling Passed/Failed every 200 ms:

- DFM receives every record, but stores only every second one.
- Final state is all status bits `false`, `occurrence_counter: 0`, so **no `Failed` was ever stored**.

Cause (fault-lib commit `12dac502`, `dfm_lib/src/fault_record_processor.rs` and `common/src/debounce.rs`):

1. On a `Passed → Failed` transition, `handle_lifecycle_transition` calls `debouncer.reset(now)`.
2. `EdgeWithCooldown::reset` sets `last_report = now`.
3. `check_debounce` then calls `debouncer.on_event(now)`: elapsed time is 0, below the cooldown, so the `Failed` event is suppressed.
4. `Failed → Passed` is not a reset transition and 200 ms exceeds the cooldown, so `Passed` events pass.

Result: a fault that recovers and fails again is never recorded when manager-side `EdgeWithCooldown` is configured. Candidate upstream issue for `eclipse-opensovd/fault-lib`.

Our Battery Thermal Guardian catalog sets all debounce fields to `null` (the Guardian debounces itself), so the DFM passes every record through and is not affected.
